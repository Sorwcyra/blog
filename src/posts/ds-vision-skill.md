DeepSeek 这类模型的能力很强，但输入只有文本。你贴一张截图过去，它拿到的是一串文件名或者干脆什么都没有。

想让它「看图」，思路无非三种：换模型、改模型、或者**在模型外面补一层**。前两个都不由我控制，所以做的是第三种。

## 定位：只做转译

`ds-vision-skill` 的边界画得很死：

```
图片 → 视觉模型 → 结构化描述 + OCR 文本 → 回灌上下文 → 原模型继续推理
```

它**不改模型、不劫持对话、不做多轮记忆**。输入一张图，输出一段模型能直接读的文字，然后退出。

这样设计的原因很实际：

1. **可替换**：视觉模型换掉，Skill 的输出格式不变，上层完全无感
2. **可审计**：模型看到的到底是什么文字，日志里能完整打到，出问题好定位
3. **不越权**：不碰对话状态，就不会和宿主自己的上下文管理打架

## 输出为什么是结构化字段

只回一句「图里有一份合同」没有意义。现在返回的是带字段的描述：

```json
{
  "type": "screenshot",
  "text": "识别出的所有文字，保留换行与顺序",
  "layout": "标题 / 正文 / 按钮 这类版面结构",
  "notes": "值得注意的细节，例如报错信息、数字、日期"
}
```

分开的好处是下游可以按需取：让它总结，就给 `text`；让它判断界面状态，就给 `layout`；排查问题，看 `notes`。

**OCR 和语义描述必须都要**。纯 OCR 会把表格读成一坨，纯描述会丢掉精确的报错码——而多数时候用户贴图就是要那个精确的东西。

## 接入成本

按 Skill 协议挂载，配置里加一行就能用，不需要改模型调用代码：

```yaml
skills:
  - ds-vision-skill
```

触发条件也做了约束：只在消息里带图片附件时才加载视觉工具，**纯文本对话不会多一次调用**，也就不会多一份 token 和延迟。

## 踩过的坑

- **图片太大**：超过视觉模型输入限制时，直接传会被截断，得先等比缩放再编码
- **长截图**：手机长截图高度动辄三千像素，模型会漏读下半部分，需要先切片再按顺序拼接结果
- **表格**：OCR 出来的表格如果没有分隔符，模型会把不同列的数字连起来读，必须显式补 `|` 或换行

这几个都是「跑通」和「能用」之间的差距，也是做这类工具真正花时间的地方。

## 结论

如果宿主模型的视觉能力短期补不上，在协议层加一层转译是最划算的做法：不用等模型更新，也不用换技术栈。
