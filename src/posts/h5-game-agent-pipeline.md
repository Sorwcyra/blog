开题定下来了：**面向 H5 游戏的智能体代码生成与自动修复系统**。所属课题组叫「AI 加速游戏制作：从模糊想法到可玩 H5 游戏的智能体流水线」，指导老师王剑涛，成果类型是论文。

写这篇不是为了介绍方案有多新，而是在动手之前，先把问题、边界和风险钉在纸上。半年之后再回来看，哪些判断对了，哪些想错了，都会写在这里。

## 一、为什么是这一段

游戏制作里最耗人的不是美术，也不是玩法设计，而是把一份结构化策划变成一个**能跑起来的工程**。

一份 H5 小游戏策划，通常包含玩法循环、关卡与数值、UI 布局、资源清单。人来做，流程大致是：搭工程、配构建、写状态机、接输入、处理资源加载、补齐边界情况（暂停、重开、失败结算），然后一遍遍刷新浏览器，看这次又白屏在哪。熟练的前端一两天，不熟的一周。中间大量时间其实花在「改一行、刷新一次」上。

让模型直接吐一个完整小游戏，这件事今天已经成立——它确实能写出几百行 JS，甚至能给出一个单文件 HTML 游戏。**问题从来不是「能不能写出来」，而是「写出来的东西能不能自动确认它是对的」。**

直接生成的产物，常见的三种死法：

- **首屏白屏**，报错埋在打包产物里，行号跟源码对不上，模型连自己错在哪都看不见
- **逻辑看着对，交互没接上**，按钮点了没反应，代码里一切正常
- **改一处坏一处**，修好 A 之后 B 崩了，改到第三轮开始来回震荡，越改越远

所以这个课题真正的落点不是「用 AI 写游戏」，而是**给生成过程装一套可验证的闭环**：每一步产出都能被机器检查，失败能被定位到具体原因，修不好能退回去换个策略。

周期从人天压到分钟，是这个闭环成立之后的结果，不是目标本身。

## 二、闭环长什么样

七段，每段之间只传结构化产物：

```
策划文档
  ↓ ① 解析：玩法 / 关卡 / 资源 / 验收点 → 结构化 JSON
任务图（DAG）
  ↓ ② 拆分：工程骨架、核心循环、UI、关卡、音效… 每个节点带验收断言
  ↓ ③ 生成：按节点生成，受 Rules（技术栈 / 目录 / 编码规范）约束
工程源码
  ↓ ④ 构建：打包、依赖检查、静态检查
  ↓ ⑤ 运行检查：无头浏览器加载，收 console、运行时异常、交互探针、截图
失败？
  ↓ ⑥ 归因：语法 / 构建 / 运行时 / 交互 / 视觉，分类并映射回源码位置与需求条目
  ↓ ⑦ 修复：局部重写，带尝试预算与历史去重
   └─ 预算耗尽 → 退回上一阶段（重新拆任务 / 降级需求），而不是无限重试
```

几个我认为不能省的判断：

**任务图必须是显式的数据结构，不是提示词里的一句话。** 拆成什么样，直接决定后面能不能并行、能不能定位、能不能回退。节点粒度我用一条很土的标准来卡：**一次生成 100–200 行，并且有一个可机器判定真假的验收条件**。达不到这标准的任务，就是拆得不够细。

**每个节点自带验收断言。** 比如「核心循环」这个节点，断言是：加载后无 console error、canvas 存在、按下空格后玩家纵坐标发生变化、若干帧内状态机从 idle 进入 running。断言和需求条目一一对应——只有对应上了，失败时才能说清是「没实现」还是「实现了但错了」。

**运行检查先看跑不跑，再看好不好看。** 截图留给最后的视觉回归，用来抓「能跑但错位 / 黑屏 / 元素叠在一起」这种断言写不出来的问题。

## 三、三个我还没有答案的难点

### 1. 工作流稳定性

Agent 工作流的失败，往往不是模型不会写代码，而是**状态在传递中烂掉**：上一步的输出格式飘了，下一步基于错误输入继续干，一路错到底，最后你只看到一个莫名其妙的白屏。

我的做法是尽量把每一步的输出钉成 schema，校验不过就重跑，而不是「尽力解析」。状态落盘，每次运行可重放——排查这类问题，没有可重放的记录基本等于瞎猜。

### 2. 代码质量控制

一次性生成整包代码，等于把几百行的隐式契约（坐标系、资源路径、状态机转换、输入优先级）全押在一次采样上。倾向的方案是**增量生成 + 强约束**：Rules 里写死技术栈和目录约定、每个节点只碰自己那部分文件、公共接口先定后写。

没想清楚的是：约束越强，模型的发挥空间越小。策划里那种「就是想要一点奇怪手感」的特殊玩法，强约束下大概率做不出来。可能需要**约束分级**——骨架强约束、玩法节点松约束——但分级边界划在哪，只能跑出来才知道。

### 3. 失败自动修复

这是整个课题最硬的一段，也是最容易做假的一段。

模型的通病是：看到一条 `Uncaught TypeError: Cannot read properties of undefined`，它并不知道是资源没加载还是数组越界，于是开始凭想象改代码，改完更糟。**修复的前提是归因**：把浏览器里那条栈，翻译成「你的 `level.js:42` 在 `tiles[y]` 为空时读了 `.id`，对应需求是第 3 关地图加载」。

打算做三件事：

- **源码映射**：sourcemap 加上需求条目反查，不让模型直接面对打包产物
- **尝试历史**：同一处、同一种改法出现过就禁止重复，避免震荡
- **修复预算**：每个节点设上限，超了就退回；退回到哪一层按错误类型定——语法错回当前节点，接口错回任务拆分，需求本身矛盾就回策划解析

能不能做到「无人值守地修到能玩」，我现在不敢保证。可验证的中间目标是两个数：**常见错误类型的自动修复率**，和**人工介入次数的下降曲线**。

## 四、怎么算做成了

课题要求里写了两条硬指标：产出可玩的 H5 游戏演示，以及与人工开发周期的量化对比报告。

「可玩」这个词得先定义，否则没法评分。我的判定分三层：

| 层级 | 判定 | 谁来判 |
|---|---|---|
| 能加载 | 无阻断性 console error，首屏 3 秒内出现画面 | 机器 |
| 能玩通 | 核心循环走完一轮：开始 → 进行 → 结算 → 重开 | 机器探针 + 人工 |
| 玩得下去 | 操作有反馈、状态可预期、没有卡死 | 人工 |

量化对比的口径也要先说清：同一份策划文档，我自己按常规流程手写一遍当基线（记人天与代码量），流水线跑一遍记「墙钟时间 + 人工介入次数 + 修复轮次」。只报「分钟级」而不报介入次数是不诚实的——如果人工介入还有几十次，那只是把工作换了个位置，没有真的省下来。

基线那部分是我自己的体力活，逃不掉，也不该逃。

## 五、条件与边界

课题有企业侧支撑：233 工坊提供 H5 技术栈与构建环境、智能体开发资产（Skills、Rules 之类）、沙箱运行环境，企业工程师提供真实业务需求与技术支持。这省掉了大量搭地基的时间，但也意味着流水线要跑在别人的工程约定上，不能自己发明一套规范然后自证自洽。

有几条打算一开始就守住：

- **生成内容的合规与安全**：游戏题材、文案、素材来源都要过一遍，工程伦理这条在开题要求里点了名
- **许可证可追溯**：依赖和素材不能为了跑通随便塞
- **执行边界**：在沙箱里跑模型生成的代码，本身就有风险，权限和能力要卡死
- **报告要对得上**：数据、结论、复现步骤三者一致，不修饰

## 六、接下来

节奏大致是：先做单节点生成加最小闭环（能跑通「生成 → 构建 → 跑起来 → 报错 → 修」的最小游戏），再扩任务图与并行，再补归因与退回策略，最后做量化对比。

第一阶段的目标很小：**让一个只有方块和键盘输入的小游戏，在无人干预的情况下跑起来，并且在自己报错之后，自己修好一次。**

这一步能成，后面才有得谈。
