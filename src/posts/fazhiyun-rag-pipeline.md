法智云要解决的问题很具体：用户问一条法规怎么理解、某个术语在法条里怎么定义，系统得给出**能追溯回原文**的答案。不能编，编了就是事故。

所以整条链路的设计目标只有两个：**召回得准**，以及**每句话都能指回出处**。

## 链路全貌

```
文档导入 → 解析 → 法律语义切块 → BGE 向量化 → Qdrant 入库
                                                  ↓
用户提问 → 查询改写 → 向量召回 + 关键词召回 → RRF 融合 → Reranker 精排
                                                  ↓
                                     LLM 生成（SSE 流式） → 引用对齐
```

看起来是标准 RAG，但每一步都有法律文本自己的麻烦。

## 一、切块：不能按字数硬切

通用做法是 512 token 一滑窗，对法条是灾难。「第 X 条」常常跨越好几个段落，硬切之后一半条文在前一块、一半在后一块，检索出来谁都不完整。

现在的做法是**按法律语义边界切**：以「第 X 条」「（一）（二）」这类条款标号作为主切分点，超长条款再按段落降级切分，并且给每块挂上元数据：

| 字段 | 作用 |
|---|---|
| 法规名称 | 回答里标注「依据《XX 法》第 N 条」 |
| 条款号 | 引用定位的最小单位 |
| 层级路径 | 章 / 节 / 条，用于上下文扩展 |

检索时命中一块，会顺带把相邻块也拿进来做上下文，避免答卷只给半句话。

## 二、检索：向量和关键词都得有

纯向量检索在法条场景会漏。原因很直白：**法条里大量是专有名词和编号**，「第一百四十三条」和「第一百四十四条」在向量空间里几乎没区别，但意思完全不同。

所以做成两路并行召回再融合：

- **向量路**：BGE embedding + Qdrant，负责语义相近的表述（「欠钱不还」↔「债务履行」）
- **关键词路**：自建倒排索引，负责术语、法名、条款号这类精确命中

两路结果用 RRF（Reciprocal Rank Fusion）合并。RRF 的好处是不用去调两路分数量纲，只看排名，工程上省掉一堆归一化的坑。

融合之后再过 **BGE Reranker** 精排，取 Top-K 进生成。重排这一步对最终质量提升最明显，因为向量召回追求的是「别漏」，重排才负责「排对」。

## 三、生成：留三条退路

生成侧不能绑死一家。现在是三条路可切：

1. 云端 API（响应快，成本可控）
2. 本地 Ollama（离线、数据不出内网）
3. 自研微调模型 `Qwen2.5-7B + LoRA`（两阶段微调，DISC-Law-SFT 数据集）

切换通过 `model_configs` 表配置，不改代码。微调模型已经发布在魔搭：`sorwcyra/fzy-law-7b`。

## 四、引用溯源：真正花时间的部分

答案里每个论断都要能落到「哪部法、第几条、原文哪一句」。实现上生成时要求模型输出结构化引用标记，落库后再和切块元数据对齐，前端渲染成可点击的角标。

这一步没法靠 prompt 糊过去——**必须让模型拿到带 ID 的上下文块，并要求它引用 ID**，否则它会把法条名编得很像真的。

## 一些工程上的取舍

- **解析走异步**：PDF/Word 解析慢且吃 CPU，全部丢给 Celery，接口只返回任务 ID
- **问答结果进 Redis 缓存**：法律问题重复率高，命中直接返回，省一次完整链路
- **后端单进程**：SSE 用同步生成器，一个长回答占住一个线程，所以启动时把 anyio 线程池调大，而不是随手加 `--workers`
- **评测用 RAGAS**：faithfulness / context_precision / context_recall 三个指标跑回归，改检索参数前后对比，不靠感觉

## 结果

技术栈：FastAPI + SQLAlchemy 2.0 + Celery / Vue 3 + Vite / MySQL + Qdrant + Redis + MinIO / LangChain + BGE + Qwen2.5-7B(LoRA)。

代码在 [github.com/Sorwcyra/fazhiyun](https://github.com/Sorwcyra/fazhiyun)，README 里有完整的本地启动步骤（三个命令跑起来）。

下一步想做的：把切块策略做成可配置的，让不同法规类型（法律 / 行政法规 / 地方性法规）能走不同的切分规则。
